## 💡 새 개념

- **DevTools = 크롬 안의 건강검진 기계**: 알아서 경고하지 않는다. 누군가 콘솔·네트워크 칸을 열어 봐야 문제가 보인다
- **DevTools MCP = Claude의 눈과 청진기**, 코드 고치기 = Claude Code의 원래 손. 둘이 합쳐져 "검사 → 원인 → 수정 → 재검사" 한 바퀴를 돈다
- **콘솔**: 화면엔 티가 안 나는 스크립트 오류가 찍히는 곳. 오류 한 줄 때문에 그 뒤 코드가 전부 멈출 수 있다
- **404**: "그런 파일 없어요". 철자 한 글자(lavendar)로도 생긴다
- **보이는 크기 ≠ 내려받는 크기**: 320px로 보여도 1400px 원본을 통째로 받으면 느리다
- **내 컴퓨터에선 빠름 ≠ 손님 휴대폰에서도 빠름**: 느린 4G 흉내를 내니 0.1초가 20.7초가 됐다
- **고정 너비(width: 860px) + 줄바꿈 금지(nowrap)**: 휴대폰에서 화면이 옆으로 넘치는 대표 원인. `max-width: 100%`로 해결
- **alt(대체 글)**: 화면 읽기 프로그램이 그림 대신 읽어 주는 설명. 검색에도 도움
- **Lighthouse**: 크롬의 자동 채점기 (접근성·권장사항·SEO, 100점 만점)
- **원본은 그대로, 복사본에서 고치기**: 실제 사이트라면 고치고 → 다시 검사하고 → 확인한 뒤 올린다

## 📝 포트폴리오 한 줄

- **문제:** 겉보기엔 멀쩡한 꽃집 웹페이지에 숨은 고장 5개가 있었고, 눈으로는 1개("느린 듯")만 찾을 수 있었다
- **해결:** Chrome DevTools MCP로 Claude가 콘솔·네트워크·모바일 화면·접근성·성능을 검사해 원인을 찾고, 복사본에서 고친 뒤 다시 검사했다
- **효과:** 문제 5/5를 찾아 고쳤고, 페이지 무게 3.4MB → 85KB, 느린 휴대폰 로딩 20.7초 → 1.7초, Lighthouse 점수 100점이 됐다

## 💬 느낀 점 (Claude가 대신 작성, 내가 확인)

- 화면은 멀쩡해 보였는데 뒤에서 오류가 3개나 나고 있었다. 눈으로는 1개밖에 못 찾아서, 도구로 들여다보는 게 왜 필요한지 알게 됐다.
- "좀 느린 듯"이라는 느낌이 숫자로 확인되니 신기했다. 느린 휴대폰에서는 20초나 걸린다는 걸 직접 보니 그림 크기가 이렇게 중요한 줄 처음 알았다.
- 복잡한 개발자 도구 메뉴를 몰라도, 말로 시키면 Claude가 검사하고 고치고 다시 확인까지 해 줘서 내가 만든 웹페이지에도 써 보고 싶어졌다.
